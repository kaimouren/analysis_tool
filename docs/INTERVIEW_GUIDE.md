# Interview guide

Use the synthetic sample, no API key, and show the critical/high findings before the aggregate score. Download the report; show effective thresholds and one observed numerator/denominator. Then run `pytest`, `python evals/run.py`, and the benchmark. Do not claim production monitoring, domain correctness, or measured real-world precision.

1. **Why build this?** Newly received CSVs need a quick, reviewable first inspection before analysis. V1 connects observed problems, explicit severity, and investigation guidance in a small offline-capable workflow.
2. **Why not just a pandas profiling wrapper?** pandas supplies primitives. This repository owns the rule policy, evidence, reproducible penalty arithmetic, deterministic ranking, independent fixture oracle, strict ingestion and export/LLM boundary. It does not claim broader coverage than dedicated profilers.
3. **What uses an LLM?** Only optional explanations, impact descriptions and conditional investigation suggestions for the first five computed issues. Every remaining report issue gets authored guidance.
4. **Why deterministic scoring?** The same observations must produce auditable results without network access, model drift or prompt variability. Run timestamps are stored outside the deterministic profile.
5. **How is severity calculated?** Centralized inclusive prevalence bands for missingness, duplicates, IQR and mixed parser results; fixed issue-class severity for other rules. Ranking uses severity/type/name. No model or inferred business impact controls it.
6. **Why those thresholds?** They distinguish increasing observed prevalence using simple policies. They are not empirically calibrated; a reviewer can override the frozen threshold dataclass and the effective policy is recorded. The absence of calibration is a deliberate disclosed limitation.
7. **What does the score mean?** One hundred minus documented capped category penalties based on cell, row, column and finite-numeric proportions. It summarizes this rule set under its effective policy.
8. **What does it not mean?** Not percent-valid data, probability of correctness, production readiness or expected model performance. A high score can coexist with a critical local finding; the UI shows a separate review status.
9. **How handle false positives?** Explain the trigger and conditional nature of each flag, keep ID/text flags advisory, preserve the original data, and require domain review. The synthetic oracle tests regression correctness, not real-world precision. No suppression workflow exists yet.
10. **Anomaly versus error?** Category and confidence are explicit. IQR is a statistical anomaly; most other findings are heuristic warnings. Empty datasets fail the structural analysis precondition. Without a business contract, a large value cannot be declared invalid.
11. **What about ten million rows?** The UI rejects inputs beyond its byte/row/cell limits. Profiling is in-memory, not streaming. Supporting this size needs a separate execution plan, bounded aggregates, explicit quantile/duplicate semantics and resource testing.
12. **Current bottleneck?** Full-frame hashing/value counts, text conversion/parsing, case grouping and intermediate arrays scale with input size; eligible integer sequence evidence sorts distinct values. Benchmarks establish total cost, not a claim of a single measured hotspot. No obvious pairwise O(n squared) loop was introduced; sorting can be O(n log n).
13. **Mixed types?** Text values are examined for numeric and date parseability, preserving observed counts and bounded local examples. The larger minority share triggers severity. CSV inference has already occurred, so lost leading zeros cannot be reconstructed.
14. **How test correctness?** Hand-calculated score cases, severity-neighbor tests, parser rejection, evidence/serialization invariants, privacy payload tests, mocked model responses, Streamlit AppTest and a real browser upload/download smoke test.
15. **How prevent detection regressions?** The planted 500-row fixture keeps its score of 92.36 and known issue classes. Eight independently authored fixtures assert exact issue identities/severities plus expected scores. CI fails on misses, extras or score changes.
16. **How evaluate the system?** `evals/run.py` generates deterministic datasets, round-trips CSV ingestion, and compares findings with expectations written from construction. It reports detections, extras, misses, fixture-relative false positives and time. Eight synthetic cases do not establish deployment accuracy.
17. **How protect sensitive data?** No upload persistence, bounded in-memory analysis, no raw-content diagnostic logging, escaped Markdown and plain-text provider prose. Hosted analysis still sends the CSV to the server. Read SECURITY.md before using sensitive data.
18. **What reaches the model?** Dataset-level aggregate metrics and penalties, plus allowlisted top-five issue fields and anonymous column aliases. No raw rows, real column names, frequency values or local parsing examples. Even aggregates can be sensitive.
19. **If the model fails?** Timeout, provider and validation failures emit a safe categorical log and return explicitly labeled authored guidance. Profiling and report export remain complete.
20. **Why an LLM at all?** It can vary explanations for readers and suggest useful investigation wording. Its benefit is optional and unmeasured here; authored guidance already provides a usable product. No explanation-quality benchmark is claimed.
21. **Architecture mistake avoided?** Giving probabilistic prose authority over measurements, severity, ranking or pass/fail. The output schema does not offer those replacement fields.
22. **Conscious tradeoff?** Bounded in-memory processing and flat modules simplify local deployment. Public profiles remain JSON dictionaries for compatibility; findings and run metadata gain typed construction boundaries instead of a broad package rewrite.
23. **How add databases?** A separate read-only ingestion adapter with explicit schema, bounded queries and credential isolation. Reuse deterministic findings; document sampling and pushdown differences. No connector is implemented.
24. **How add pipelines?** A stable JSON artifact and explicit contract-based exit criteria, separate from the heuristic aggregate score. Current CLI evaluation tests the tool, not arbitrary customer data gates.
25. **How add schema drift?** Persist versioned schema snapshots with provenance and compare declared/inferred fields between compatible datasets. V1 has no persistence or historical baseline.
26. **How productionize for a company?** First define ownership, data sensitivity, workload, quality contracts and failure budgets. Then add host-level identity, quotas, egress policy, dependency/security review and representative concurrency tests. V1 supplies neither an enterprise service nor those guarantees.
27. **Why not Great Expectations?** GX validates declared expectations through validation definitions and suites. That is a good fit when a team owns explicit data contracts. V1 explores an unfamiliar CSV with generic heuristics; it is not a replacement for a mature validation framework. [GX validation documentation](https://docs.greatexpectations.io/docs/core/run_validations/).
28. **Why not Soda?** Soda provides declared contracts/checks and operational tooling. V1's scope is a bounded CSV review and portable report. If the need becomes operational monitoring, evaluate established tools before expanding this repository. [Soda reference](https://docs.soda.io/reference).
29. **Another week?** Gather representative, consented datasets and reviewer labels; measure false positives and explanation usefulness; add explicit schema/NA parsing options before broadening integrations. Tighten deployment reproducibility from the environment evidence.
30. **Hardest engineering problem?** Making precise counts useful without pretending their interpretation is certain. Separate evidence from inference, show denominators, preserve uncalibrated-policy caveats and keep model prose subordinate to facts.

## Most challenging follow-ups

Be ready to defend weight calibration, correlated penalties, missingness dilution across wide schemas, exact-versus-approximate scaling, ambiguous parsing, synthetic evaluation coverage, plain-language hallucinations that pass validation, hosted-data boundaries, concurrent memory/cost abuse, and why operational platforms were kept outside V1.


## V1.2 seven-question defense

1. **Why can a high score coexist with a critical issue?** The score averages prevalence across cells/columns. A fully missing column can be diluted by many clean columns. Its local severity remains critical and is independently displayed.
2. **What does the score measure?** The documented capped penalty total under the effective heuristic policy, subtracted from 100. It is reproducible arithmetic, not calibrated data validity or model readiness.
3. **Why separate severity and score?** Severity prioritizes an individual rule finding; score summarizes aggregate signals. Neither safely substitutes for the other or establishes business impact.
4. **Why cannot the LLM alter findings?** Measurements and policy decisions must remain reproducible, auditable and available offline. Model variability must not determine correctness or ranking.
5. **What guarantees apply to generated prose?** Expected schema/IDs/order and narrow lexical constraints are checked; rejected output falls back safely and cannot overwrite deterministic facts. There is no semantic-verification guarantee, and paraphrased falsehoods remain possible.
6. **Why is CSV inference uncertain?** It guesses types and missing conventions before profiling. Zero padding, NA-like categories and numerical precision can change. Bounded pre-inference examples reveal some ambiguity but are not a lossless representation.
7. **What next, and why contracts?** Explicit types, null conventions, keys and business constraints would distinguish intended behavior from guesses. That is more valuable than accumulating generic heuristics whose false positives cannot be resolved without context.
